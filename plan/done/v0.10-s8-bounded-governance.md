## 1. Name

`bounded-governance-addons`

## 2. Scope

Add bounded, advisory governance signals to runs and sessions without introducing a standalone approval engine, budget enforcement platform, or org-chart model.

This slice covers:

- run/session-level `--goal` flag for goal binding
- operator-facing cost/budget summaries after execution
- surfacing `approval_required`, `supervision_required`, `confidential_execution` signals from the expertise layer into lifecycle events and CLI output

This slice does NOT cover:

- approval workflow engine
- budget enforcement platform
- org/company operating model
- automatic policy enforcement or blocking based on governance signals

## 3. Design

### 3.1 Goal Binding

Add `--goal <text>` flag to `mah run` and `mah delegate --execute`:

```
mah run --goal "Fix auth bug without breaking existing sessions" -- "Fix the login timeout issue"
mah delegate --execute --goal "Refactor DB layer safely" --target backend-dev --task "Refactor connection pooling"
```

- Goal text is persisted in the session's lifecycle events as a `goal` field on the `queued` event.
- Goal text appears in `mah sessions status` output.
- Goal is advisory — MAH does not enforce goal compliance automatically.
- Goal is included in explain/trace output when present.

### 3.2 Cost/Budget Summaries

After execution completes, include an optional cost summary in the `completed` lifecycle event:

```json
{
  "event": "completed",
  "goal": "Fix auth bug without breaking existing sessions",
  "cost_summary": {
    "duration_ms": 12453,
    "evidence_records": 2,
    "context_docs_loaded": 1,
    "lifecycle_events": 5
  }
}
```

- Summary is informational only — no enforcement.
- Exposed in `mah sessions status` text output as compact line.
- Exposed in `--json` output as structured block.
- No token counting or dollar-cost estimation — keep to MAH-internal metrics.

### 3.3 Governance Signal Surfacing

The expertise layer already has `trust_tier`, `approval_required`, `supervision_required`, and `confidential_execution` fields. Surface these into:

- `mah expertise explain` output: show governance signals per agent when present
- `mah run --trace` output: show governance state of selected agent
- Lifecycle events: include governance signals in `routed` event

Example trace output:
```
Governance: trust_tier=standard, approval_required=false, supervision_required=false, confidential_execution=false
```

### 3.4 Design Constraints

- All governance signals remain advisory and informational.
- No run is blocked or rejected based on governance signals alone.
- No standalone approval workflow is introduced.
- No budget hard-limit enforcement.
- Signals are best-effort — missing signals degrade gracefully.

## 6. Risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| `--goal` creates expectation of automatic goal compliance checking | Medium | Docs clearly state advisory-only; no compliance engine |
| Cost summary metrics are too thin to be useful | Low | Start with MAH-internal metrics; extend later if operators request more |
| Governance signals in expertise are sparse or always default | Medium | Surface only when non-default; avoid noise |
| Scope creep into approval workflows | Medium | Strict boundary: no blocking, no enforcement, no approval engine |

## 7. Dependencies
